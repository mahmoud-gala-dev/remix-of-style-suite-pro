# Audit Cycle #16 — 2026-06-22 — Enterprise scale-out

## Focus
Implement the four enterprise gaps surfaced in the previous evaluation:
1. Cache layer (KV/Redis equivalent) for reports
2. Job queue for batched notifications
3. Materialized views for aggregate reports
4. Multi-region read replicas

## Changes

### 1. Report cache (DB-backed KV)
- Migration: new `report_cache` table (key/payload/expires_at), `cleanup_report_cache()` SECURITY DEFINER function, service_role-only grants, RLS enabled.
- `src/lib/report-cache.server.ts`: `cached(key, ttlSec, loader)` helper + `reportKey()` builder. Failures degrade to miss — never throw.
- `src/lib/reports.functions.ts`: `getReportsSummary` and `getReportsCompare` wrapped with 60 s TTL.
- pg_cron job `cleanup-report-cache` runs every 15 min.
- Note: Cloudflare Workers KV / external Redis are not provisioned on Lovable Cloud; a Postgres-backed KV gives the same hit-rate benefit without new infra.

### 2. Notification job queue
- Migration: new `notification_jobs` table (kind/payload/status/attempts/run_at), partial index on runnable rows, service_role-only grants, RLS enabled, `updated_at` trigger.
- `src/lib/notification-queue.server.ts`: `enqueueNotification(kind, payload, runAt?)` helper.
- `src/routes/api/public/cron/drain-notifications.ts`: claims a batch of 25 rows atomically (status → 'sending'), runs them, on failure backs off exponentially up to 5 attempts.
- `src/lib/bookings.functions.ts`: `createBooking` now enqueues `booking_confirmation_email` instead of awaiting Resend inline. Booking response is no longer blocked on third-party latency.
- pg_cron job `drain-notifications` runs every minute.

### 3. Materialized views for aggregate reports
- pg_cron job `refresh-mv-daily-revenue` schedules existing `refresh_mv_daily_revenue()` every 10 min.
- `getDailyRevenue` server fn added — reads from `mv_daily_revenue` directly (constant-time vs. O(bookings) aggregation in `getReportsSummary`).
- Locked down `refresh_mv_daily_revenue()` EXECUTE to service_role only.

### 4. Multi-region read replicas → CDN edge cache (the honest substitute)
- True read replicas require Supabase Enterprise + a DB router; not available on Lovable Cloud.
- Substitute: HTTP cache headers with `s-maxage` + `stale-while-revalidate` so Cloudflare's PoPs serve repeat hits geographically without hitting Postgres.
- `src/routes/sitemap[.]xml.ts`: upgraded `Cache-Control` to `public, max-age=600, s-maxage=3600, stale-while-revalidate=86400`.
- Healthcheck stays `no-store` (correct — must always reflect live DB state).

- 3 new pg_cron jobs scheduled: `cleanup-report-cache` (15 min), `drain-notifications` (1 min), `refresh-mv-daily-revenue` (10 min).
