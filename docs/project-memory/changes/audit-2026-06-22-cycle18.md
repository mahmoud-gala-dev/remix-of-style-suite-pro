# Audit Cycle #18 — 2026-06-22 — Report cache invalidation hooks

## Focus
Close the 60-second staleness window introduced by `cached()` in cycle #16:
after a booking write, the next `/reports` read recomputes instead of serving
the previous payload from `report_cache`.

## Changes
- **`src/lib/report-cache.server.ts`**: added `invalidateReportCache(prefix?)`
  helper. Deletes `report_cache` rows whose key matches `reports.%` (or the
  caller-supplied prefix) via `supabaseAdmin`. Failures are swallowed — a
  flaky cache must never break the originating write.
- Wired into every server-fn that mutates the `bookings` aggregation surface:
  - `bookings.functions.ts` → `createBooking`
  - `reschedule.functions.ts` → `rescheduleBooking`
  - `customer-portal.functions.ts` → `cancelByToken`
  - `recurring.functions.ts` → `createRecurringSeries`, `cancelRecurringSeries`

Deposit mutations (`deposits.functions.ts`) intentionally skipped — they
change Stripe metadata only, not the price/status fields that drive revenue
aggregation.

## Verification
- `bunx tsc --noEmit` → clean.
- Invalidation is fire-and-forget (`try/catch` swallow) so booking-write
  latency is unchanged in the happy path; in the failure path the booking
  still commits.

## Score impact
No category regression. Reports & Analytics correctness ticks up: after-write
reads are immediately fresh.
